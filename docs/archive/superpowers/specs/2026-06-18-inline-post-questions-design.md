# Inline Post Questions Design

## Summary

Add public, sentence-level discussion threads inside published posts. Readers can select text in a post, the selection expands to the full sentence or sentences touched by that selection, and a **Đặt câu hỏi** action lets them ask a question about those sentences.

The feature behaves like the current comment system, but anchored directly to article text instead of the whole post. Other readers can click highlighted sentences and join the same conversation.

## Product Behavior

- Readers select text inside the post body.
- The app expands the selection to every full sentence touched by the selected text.
- The expanded sentence range is preview-highlighted before submission, so the reader understands exactly what will be used as the question anchor.
- Clicking **Đặt câu hỏi** opens a form with the same guest fields as comments:
  - name
  - email
  - question/comment text
  - reply notification preference
- Submitted questions create a public conversation thread attached to those sentence anchors.
- Existing question anchors render as visible inline highlights in the post.
- Clicking an existing highlight opens its conversation.
- Other readers can reply and join the thread, just like the normal comment section.
- The normal bottom comment section remains unchanged.

## Layout Behavior

- Desktop:
  - Open the selected/highlighted conversation in a side panel beside the post, preferably on the left side of the article area.
  - Keep the article readable while the panel is open.
- Mobile:
  - Open the conversation in a modal or bottom sheet.
  - The modal/bottom sheet should show the anchored sentence quote at the top, followed by the thread and reply form.

## Anchor Rules

- A text selection is never stored as only the exact selected substring.
- The stored anchor is the full sentence or full sentences containing the selected text.
- If the reader selects across multiple sentences, all touched sentences are included.
- If the reader selects a few words inside one sentence, only that sentence is included.
- If a reader tries to create a question on the exact same sentence set as an existing active thread, open the existing thread instead of creating a duplicate.
- If multiple different threads overlap the same sentence, clicking the highlighted sentence should show a small thread picker/list in the side panel or modal.

## Content Edit Rules

- Conversations should be tied to sentence text anchors, not fragile DOM offsets only.
- Store normalized sentence text and stable hashes for every sentence in the selected anchor.
- When a post is updated or published:
  - Recalculate the current sentence hashes from the updated post body.
  - If an inline question thread has at least one stored sentence hash still present, keep it active.
  - If none of the stored sentence hashes are still present, archive the thread and hide it publicly.
- Do not hard-delete these threads from the database. Archive them so admins can inspect/recover later if needed.
- Authors are expected to understand that deleting all anchored sentences hides the related conversation.

## Data Model

Add new models instead of overloading the existing `Comment` table.

Suggested models:

- `PostQuestionThread`
  - `id`
  - `postId`
  - `status`: `ACTIVE | ARCHIVED`
  - `anchorText`: original selected sentence block for display
  - `sentenceTexts`: stored selected sentences
  - `sentenceHashes`: normalized hashes used for reconciliation
  - `createdAt`
  - `updatedAt`
  - `archivedAt`
- `PostQuestionComment`
  - `id`
  - `threadId`
  - `postId`
  - `parentId`
  - `authorName`
  - `authorEmail`
  - `authorId`
  - `content`
  - `status`: same public moderation behavior as comments for v1
  - `notifyReply`
  - `createdAt`

Privacy rule: never expose `authorEmail` from public APIs.

## API Shape

Use the existing API response convention:

- Success: `{ data: T }`
- Error: `{ error: string }`

Suggested routes:

- `GET /api/posts/[postId]/questions`
  - Returns active question threads for a published post.
  - Includes public comments/replies for each thread.
  - Excludes archived threads and private email fields.
- `POST /api/posts/[postId]/questions`
  - Creates a thread plus the first question.
  - Accepts guest fields or uses authenticated session user.
  - Accepts the selected sentence texts/hashes generated by the client and validates they still exist in the current post body.
- `POST /api/posts/[postId]/questions/[threadId]/comments`
  - Adds a reply to an existing active thread.
  - Uses the same guest/auth behavior as normal comments.

## UI Components

Suggested components:

- `InlineQuestionLayer`
  - Wraps or sits beside `PostBody`.
  - Tracks text selection inside `.post-content`.
  - Expands selection to sentence anchors.
  - Renders temporary preview highlight and action button.
  - Renders persistent highlights for active question threads.
- `InlineQuestionPanel`
  - Desktop side panel / mobile modal.
  - Shows anchored sentence quote, thread comments, and reply form.
- `InlineQuestionForm`
  - Reuses the current comment form behavior where practical.
  - Button labels should use question wording for first submission and reply wording for replies.
- `InlineQuestionThreadList`
  - Displays comments/replies for the selected anchor thread.

## Sentence Extraction

- Use `Intl.Segmenter` for sentence splitting when available.
- Provide a regex fallback for environments without `Intl.Segmenter`.
- Normalize sentence text by:
  - trimming
  - collapsing whitespace
  - lowercasing
  - hashing the normalized result
- Exclude non-readable article UI from anchoring:
  - code blocks
  - media controls
  - buttons
  - captions can be included only if the implementation deliberately supports them; default v1 can exclude captions.

## Notifications

- New top-level inline questions should notify the post author and accepted coauthors, similar to post comments.
- Replies should notify the parent comment author when `notifyReply` is enabled.
- Avoid duplicate emails when the same person is both post author and parent comment author.
- Email links should open the post and focus/open the relevant inline question thread.

## Admin and Moderation

- Admin should be able to see inline question threads and comments.
- Archived threads should be admin-visible but hidden from public post pages.
- V1 can reuse the existing simple status model: `APPROVED` and `SPAM`.
- If normal comments have spam moderation actions, inline question comments should eventually support the same actions.

## Testing Plan

Unit tests:

- Selection expands to the full containing sentence.
- Selection spanning multiple sentences includes all touched sentences.
- Sentence normalization/hashing survives whitespace and casing changes.
- Reconciliation archives a thread only when all selected sentence hashes disappear.
- Public API serializers never include `authorEmail`.

API tests:

- Guest users must provide name and email.
- Authenticated users can submit without guest fields.
- Creating a question fails if the selected sentences no longer exist in the current post.
- Replies cannot attach across posts or threads.
- Archived threads are not returned publicly.

UI tests:

- Selecting post text shows **Đặt câu hỏi**.
- Preview highlight covers full sentence(s), not only selected words.
- Existing highlights open the correct thread.
- Desktop uses side panel.
- Mobile uses modal or bottom sheet.

E2E tests:

- A reader creates an inline question from selected text.
- Another reader opens the highlight and replies.
- An author edits away all anchored sentences and the thread disappears publicly after reconciliation.

## Assumptions

- The feature is public and reader-facing.
- The action label should be **Đặt câu hỏi**.
- Anyone can join an inline question conversation.
- The normal bottom comment section remains separate.
- Conversation deletion after content edits means archive/hide publicly, not hard delete.
- Inline question counts should not affect normal post comment counts in v1 unless a later product decision changes that.
